## Day 1 | Neon Postgres 버전
- 상황: 로컬은 PostgreSQL 16.15. Neon 프로젝트 생성 화면에서 버전 선택
  항목을 찾지 못해 기본값으로 진행 → 실제 생성된 버전은 18.6
- 판단: 그대로 진행
- 근거: 이관 대상이 CREATE TABLE / CHECK / FK / 인덱스 수준이며
  16→18 사이에 해당 구문의 호환성 변경 없음.
  하위 버전에서 상위 버전으로 올리는 방향이라 pg_dump 출력에
  대상 버전이 모르는 구문이 섞일 위험도 없음
- 감수하는 것: 로컬과 운영 DB의 버전 불일치.
  실무라면 개발/운영 버전을 일치시키는 것이 원칙이며,
  버전 차이로 인한 동작 차이는 이 프로젝트 범위에서만 무시 가능
- 확인 방법: python src/test_conn.py 출력의 version() 결과

## Day 3 | raw 스키마 설계 3건

### batch_date를 PK에 포함하지 않음
- 선택: 원본 PK 유지, batch_date는 일반 컬럼 + 인덱스
- 이유: 재생 방식에서 같은 행이 두 번 도착하지 않음.
  복합키로 만들면 FK도 복합키가 되어, 고객과 주문이 서로 다른 배치에
  들어올 때 참조가 깨짐
- 멱등성 확보 방법: 트랜잭션으로 묶은 DELETE(batch_date) → INSERT
- 감수하는 것: 같은 PK가 다른 날짜로 재도착하면 배치 실패.
  단, 이는 조용히 덮어쓰는 것보다 알람이 울리는 편이 낫다고 판단

### ck_clickstream_time_range 제외
- 원본: CHECK (event_time BETWEEN '2025-09-01' AND '2025-12-03')
- 문제: 수집 기간이 하드코딩되어 재생으로 날짜를 이동시키면 전 행 거부
- 조치: raw 스키마에서 제외하고 검증 룰 R15로 이관.
  고정 범위 대신 "event_time이 batch_date ±7일 이내" 상대 기준 사용
- 결과: CHECK 26 → 25
- 유지한 것: ck_orders_date, ck_customer_dob_past는 CURRENT_DATE 기반이라
  시점에 관계없이 의도대로 동작하므로 유지

### 인덱스 13개 → 8개로 축소
- 유지: batch_date 6개, orders의 FK 컬럼 2개, clickstream.customer_id
- 제외 근거: 원본 인덱스는 탐색·정제 단계의 쿼리 패턴에 맞춰진 것.
  운영 파이프라인은 batch_date 진입이 대부분.
  인덱스는 용량(무료 0.5GB)과 INSERT 속도에 비용을 발생시킴
- 추가 원칙: 대시보드가 느려지면 EXPLAIN ANALYZE로 측정 후 필요한 것만 추가

## Day 3 | 재생 기준일(ANCHOR) 확정
- ANCHOR = 2026-09-28. 이 날이 재생 1일차이며 논리 날짜 2025-09-02에 대응
- 92일 순환: 2026-12-28에 1회차 종료, 이후 논리 날짜가 2025-09-02로 복귀
- 상태 파일을 쓰지 않고 실제 날짜로 계산하는 이유:
  GitHub Actions는 매 실행마다 새 러너가 뜨므로 상태가 유지되지 않음.
  상태 파일을 레포에 커밋하면 배치가 매일 커밋을 생성해 이력이 지저분해짐
- --date 인자로 과거 배치 백필 가능. ANCHOR 이전 날짜는 ValueError로 차단
- **변경 금지**: 적재 시작 후 ANCHOR를 바꾸면 논리 날짜가 전부 어긋남

## Day 3 | undated 배분 방식
- 92등분이 아니라 원본 결측률 기준으로 개수 산정
  n_null = n_dated × r / (1 - r)
- 이유: 92등분 시 orders 결측률이 77%로 원본(30%)과 크게 어긋나
  D01 룰의 기준선이 성립하지 않음
- 풀은 고정 시드(42)로 한 번 섞은 뒤 day_index 위치부터 순차 소비 →
  조각 간 편향 없음, 재현 가능
- 한계: support_tickets는 일 40건 규모라 정수 반올림으로 결측률이
  8~10% 사이에서 흔들림. D01 임계값을 ±10%p 로 넉넉히 잡을 것

  ## Day 3 | Parquet의 UUID 처리
- 문제: Parquet에 UUID 타입이 없어 16바이트 이진값으로 저장됨.
  다시 읽으면 b'\xfa\x10...' 형태가 되어 uuid 컬럼 적재 시 타입 오류
- 조치: 추출 단계에서 astype("string")으로 문자열 변환.
  적재 시 Postgres가 다시 uuid로 해석
- astype(str)이 아닌 astype("string")을 쓴 이유: 전자는 NULL을
  "None" 문자열로 바꿔버림. clickstream.customer_id는 30%가 NULL이라 치명적
- 용량: 42.3 → 77.6 MB (UUID 16바이트 → 36글자). DB 용량은 불변(uuid는 16바이트 고정)
