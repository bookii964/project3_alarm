# 검증 룰 카탈로그

`src/validate.py` 가 실행하는 룰의 전체 목록이다.
기준값은 `config/baseline.yml`, 알람 배정은 `config/alerts.yml` 에 있다.

## 처리 구분

| 구분 | 의미 | 결과 |
|---|---|---|
| **격리** | 해당 행만 빼고 나머지는 정상 적재 | `quarantine.rejected_rows` 에 원본 보관 |
| **경고** | 적재는 그대로 하되 기록 | `mart.dq_daily` 에 FAIL/WARN 기록 |

행 단위로 판정 가능한 것은 격리하고, 집합 전체를 봐야 하는 것은
경고로 둔다. 격리는 데이터를 빼내는 행위라 판정 근거가 명확해야 한다.

## 구현된 룰 (9종)

### C — 계약 검증

데이터의 모양이 기대와 같은지 본다. 가장 먼저 실행된다.

| ID | 내용 | 처리 | 비고 |
|---|---|---|---|
| **C03** | PK 중복 | 격리 | `keep="first"` 로 첫 행만 남긴다 |
| **C05** | 적재 0건 | 경고 | 상류 중단 또는 수집 대상 없음 |

C03 은 운영 중 한 번도 발동하지 않았다. 다만 **개발 과정에서
재생기 버그를 잡아냈다** — undated 풀의 소비 구간이 겹쳐 같은 주문이
이틀 연속 들어왔을 때, DB 의 PK 제약이 먼저 거부했다.

### X — 참조 무결성

| ID | 대상 | 참조 | 처리 |
|---|---|---|---|
| **X01** | orders.customer_id | crm_customers | 격리 |
| **X02** | orders.product_id | product_catalog | 격리 |
| **X03** | support_tickets.customer_id | crm_customers | 격리 |
| **X04** | clickstream.customer_id | crm_customers | 격리 |
| **X05** | clickstream.product_id | product_catalog | 격리 |
| **X06** | crm_customer_devices.customer_id | crm_customers | 격리 |

**NULL 은 검사 대상이 아니다.** clickstream.customer_id 는 30%가
비로그인 이벤트라 NULL 이며, 이는 정상이다.

#### 참조 대상을 어디서 가져오는가

DB 의 기존 마스터 + **이번 배치에 들어올 신규 마스터**를 합쳐 대조한다.
오늘 가입한 고객의 오늘 주문은 유효해야 하기 때문이다.

DB 조회는 id 컬럼만 가져온다. 4만 행이라도 1MB 수준이라 부담이 없다.

#### X02 / X05 / X06 은 발동한 적이 없다

상품과 기기는 마스터가 먼저 전량 적재되므로 고아행이 생기지 않는다.
반면 고객은 증분 공급이라 "가입 전 활동"이 걸린다.

### D — 분포 검증

집합 전체를 봐야 알 수 있는 것들이다. **행 하나하나는 멀쩡한데
전체를 보면 이상한 경우**를 잡는다.

| ID | 내용 | 처리 | 임계 |
|---|---|---|---|
| **D01** | 컬럼별 결측률 vs 기준선 | 경고 | ±10%p |
| **D02** | 범주형에 허용되지 않은 값 | **격리** | 1건이라도 |
| **D05** | 적재량 vs 기준선 | 경고 | ±50% |
| **D08** | 격리율 | 경고 | 3% **그리고** 10건 |

## 설계 판단

### D02 를 격리로 승격한 이유

처음에는 경고로만 두었다. 주입 시나리오에서
`payment_method = 'bitcoin'` 3건이 들어오자 `ck_orders_payment`
CHECK 제약에 걸려 **배치 전체가 실패**했다.

격리로 바꾸니 3건만 빠지고 나머지 367행이 정상 적재됐다.

**검증 룰이 DB 제약보다 넓거나 같아야 한다**는 원칙이 여기서 나온다.
DB 가 거부할 것을 검증이 먼저 걸러야 파이프라인이 살아남는다.

### D08 에 절대 건수 조건을 더한 이유

비율만 쓰면 행 수가 적은 테이블에서 오탐이 난다.

support_tickets 40건 중 3건 격리 = 7.5% → 비율 초과
clickstream 5,400건 중 77건 격리 = 1.4% → 통과


같은 3건인데 테이블 규모 때문에 판정이 갈린다.
운영 초기 7일 중 3일에서 오탐이 발생해 조건을 추가했다.

### 참조 무결성 룰은 매일 FAIL 이지만 알람을 보내지 않는다

X01/X03/X04 는 이 데이터셋의 상수에 가깝다.
`mart.dq_daily` 에는 FAIL 로 기록하되, 알람은 **기준선의 3~5배를
넘을 때만** 보낸다.

기록과 알림을 분리한 것이다. 대시보드에서는 추세를 볼 수 있고,
Slack 은 조용하다.

## 미구현 룰

설계는 했으나 2주 일정에서 제외한 것들이다.
목록을 남겨두는 것은 "알고 있지만 우선순위로 판단했다"를 기록하기 위함이다.

### 계약 검증

| ID | 내용 | 제외 사유 |
|---|---|---|
| C01 | 컬럼 집합 변경 감지 | 재생 데이터라 스키마가 고정 |
| C02 | 컬럼 자료형 검증 | 위와 동일 |
| C04 | NOT NULL 위반 | DB 제약이 이미 막음 |

실제 운영이라면 C01 이 가장 중요하다. 상류가 말없이 컬럼을 바꾸는
사고가 흔하기 때문이다. 재생 방식에서는 발생할 수 없어 뺐다.

### 행 단위 값 검증 (R01~R15)

`raw` 스키마의 CHECK 제약 25개가 같은 역할을 한다.
검증 룰로 중복 구현하는 대신 **DB 제약에 맡기고, 위반 시
배치가 실패하도록** 두었다.

다만 이 선택에는 한계가 있다. DB 제약은 "뭔가 잘못됐다"만 알려주고
"몇 건이 어떤 사유로"를 알려주지 않는다. D02 사례처럼
**검증으로 끌어올려야 하는 룰이 더 있을 수 있다.**

### 분포·정합성

| ID | 내용 | 제외 사유 |
|---|---|---|
| D03 | 범주 분포 급변 (비중 변화) | 구현 가능하나 임계 설정에 데이터 부족 |
| D04 | 수치 분포 급변 (중앙값) | 위와 동일 |
| D06 | `_flag` 발생률 추이 | **아쉬운 제외** — 정제 이력을 감시하는 룰 |
| D07 | 중복 행 비율 | C03 과 중복 |
| X05 | clickstream purchase 이벤트 출현 | 원본에 없는 이벤트. 나타나면 수집 로직 변경 신호 |
| F01~F04 | 신선도·적시성 | `mart.batch_log` 와 알람 P1 이 대체 |

**D06 이 가장 아쉽다.** `_flag` 는 정제 단계에서 "왜 이 값을 비웠는지"를
기록한 컬럼인데, 그 발생률이 변한다는 건 상류 데이터의 성질이
바뀌었다는 뜻이다. 28일 이상 기준선이 쌓이면 추가할 만하다.

## 룰 추가 방법

1. `config/baseline.yml` 에 기준값 정의
2. `src/validate.py` 의 `validate()` 에 판정 로직 추가
3. `config/alerts.yml` 의 `rule_severity` 에 심각도 배정
4. `config/alerts.yml` 의 `rule_info` 에 의미·원인·조치 작성
5. `docs/07_runbook.md` 에 대응 절차 추가

4번을 빠뜨리면 Slack 알람에 룰 ID 만 나와 담당자가 대응할 수 없다.
